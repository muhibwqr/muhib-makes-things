how to create long horizon harnesses

november 17th, 2026 · 22 min

Preface

a long horizon agent keeps working toward one goal for months, long after the chat ends.

its harness is the software around the model: tools, memory, permissions and a loop that keeps it running.

Overview

  1. where long-running agents are today
  2. what a long horizon harness is, and the nine layers it needs
  3. an architecture you can copy
  4. why build one, and related ideas
  5. case studies in agent businesses, medtech and fintech
  6. the biggest objection, and open questions

As we see more and more businesses implement basic agents, long horizon agents and comprehensive harnesses, they remind me of goldfish. Most agents can't remember enough to make it past one lap of the tank, and even the ones that can often need something outside their tank to finish the task. I want to introduce the concept of a long horizon harness. Imagine a tiny, fragile goldfish with access to a tank that can change into whatever it needs to complete a task. It has an external memory system that sits right outside its tank, and it references it every single day.

This is more important now than ever because models are getting longer legs fast. METR found that the length of task frontier agents can finish has doubled about every seven months since 2019. But METR measures tasks that take a human hours, not months, and health and money run on months.

A lot of cool long-running functions already exist. Karpathy's autoresearch lets an agent run ML experiments overnight: it edits the training code, trains for five minutes, keeps or discards the change, and repeats until you wake up to a log of experiments. Claude Code's /loop and cron tools run a prompt on a schedule to poll for status or set reminders. Instinct, Muse and Duet, Rubric Labs' always-on agents, wake on a heartbeat and on events in the world, not just on prompts. Each one stretches an agent past a single chat. My initial prediction was that we would see more long horizon harnesses in the following weeks. However, as I was writing this, Replit Missions and Devin Bots came out on the same day. In Replit Missions, you define an outcome, a budget and which actions need your approval, and a swarm of agents plans, builds, tests and iterates toward it. It can run for days, but keeping a result true afterward is a different problem. Devin Bots are persistent agents you give "a responsibility, not a task", like "keep Android at parity with iOS". The frontier is now agents owning an outcome rather than a task. This article is about owning a promise, and maintaining it.

what a long horizon harness is

A long horizon agent is an agent that can keep working toward a goal over months and has the resources and context to continue, while a harness is a toolkit for this agent.

In its simplest form, a long horizon harness can be defined as the system around an agent that keeps a goal true over months, long after any single session, model or person has moved on.

so what makes up a long horizon harness.

Fundamentally, there are nine layers to the long horizon harness.

1. intent

Define a verifiable goal and a timeline that the agent can hit and maintain. A simple shape is "keep X true until Y", like "keep at least 12 months of cash in the bank (X) until the next fundraise (Y)". If you can't check it, the harness can't keep it.

2. contract

Turn the intent into claims a program can check, each with a deadline, e.g. "nothing should ever reach more than 5 days overdue".

3. ledger

Think of this as a source of truth: the goal is a memory that lives outside the model, which the harness can reference every time it wakes.

Memory also needs upkeep. Over months, writes pile up as duplicates, contradictions and stale entries, so recently the frontier has started to “dream”: an offline pass that cleans memory between sessions. Claude's dreams read a memory store and up to 100 past sessions, merge duplicates, replace stale or contradicted entries and surface new insights. Devin's dreaming runs daily over memories kept as markdown files in a Git repository, deduplicating them and linking them to the sessions they came from. Google's sleep framework goes further and consolidates into the model itself, alternating a wake phase with a sleep phase so it can keep learning without forgetting. For a long horizon harness, dreaming is not only ledger maintenance, which keeps months of memory small and true, but also an iterator. It can spot patterns and propose changes to the classifier, the evals, the heartbeat or the hands, but it never grants itself new permissions; a human approves.

4. heartbeat

Heartbeats are set by a human, not the agent. Define each one as specifically to your domain as you can. A consistent daily cadence may be effective for some cases, whereas for others hourly may be better.

5. senses

List the sources the harness can read, and the things it can't see and has to ask a human about.

6. hands

Define the actions you're okay with the agent taking within your domain to maintain your goal. These are normally adjustment tasks: something reversible that doesn't have a critical impact, like sending a reminder or pausing a task. Everything else goes to a human.

7. judgment

This is best defined as a playbook that filters which actions to take. A model I find useful: strict action cases, lenient wait cases and broad escalation clauses. In the diagram, this playbook is the classifier: every heartbeat passes through it and comes out as act, nothing or escalate.

8. handoff

Every time the agent has a heartbeat, it writes a short note: what it saw, what it did and what's next, so a new agent, a new model or a person can continue.

9. evals

These are the tests that verify results. The harness can recommend changes to the evals, but only a human can approve them. Standing evals check the result and only a human can change them. Posture evals check how the harness behaves, and the harness can propose and improve them. Because a wrong "nothing" fails silently, a human should also spot-check a sample of the "nothing" calls.

I really like Anthropic's guide to agent evals. It separates the transcript from the outcome: a booking agent saying "your flight is booked" doesn't count; only a real reservation in the system does. It also separates pass@k, getting it right at least once in k tries, from pass^k, getting it right every time. A long horizon harness runs the same check hundreds of times, so getting it right every time is what matters: an agent that works 75% of the time only gets three in a row right about 42% of the time. And when you evaluate an agent, you're evaluating the harness and the model together.

There should be an iterative loop that notices patterns and molds the harness around them. If people keep getting the same alert, or a check keeps finding nothing, the harness suggests a change to its own rules, and a human approves it.

why

Now at this point, you may be wondering, why the heck would I even implement this?

  • !=a chatbot: it answers well from context, but its horizon is too short.
  • !=rules or a cron job: while this option is cheap and can give a regular, reliable update, on its own it can't handle anything not accounted for.
  • !=an always-on agent: it wakes on its own and reacts to events, but it tends to act too often, with no fixed promise and no proof that it held.
  • !=one long agent run: it can finish a big task over hours or days, but it stops at done, so nothing keeps the result true afterward.

A long horizon harness will allow you to keep what each one is good at: the rules' reliability, the agent's judgment and the always-on wake-up. It also adds what they're all missing: a promise you can check, a memory checked against the real world, small actions that can be undone, and a human for everything else. The result is fewer missed follow-ups, fewer unnecessary alerts, and a log that shows why it did or didn't act.

As I've been improving how I work and build with agents and harnesses, I was intrigued to see Replit and Devin drop adjacent features on the same day. My gut tells me that in the coming weeks we will see more long horizon harnesses.

related ideas

An adjacent yet popular idea is recursive self-improvement (RSI): an AI system that iteratively builds a more capable successor. It's mostly still a hypothesis, but the early working versions improve the harness, not the model. The Darwin Gödel Machine rewrites its own agent code, keeps an archive of every version, and checks each change against coding benchmarks. In my mind, the benefits are more like harness adjustments: better editing tools, long-context management and peer review. That took it from 20% to 50% on SWE-bench. Autoresearch has the same shape: change, test, keep or discard, repeat. Every RSI loop needs what a long horizon harness provides: a memory of what was tried, a contract for "better", and a heartbeat that keeps it going, all inside a sandbox with human oversight. Put side by side, a harness gives an agent tools, an always-on agent gives it a heartbeat, a long horizon agent gives it a goal that lasts, and RSI gives it a way to improve itself; a long horizon harness is what holds all four together, so the goal survives every session, every model and every improvement.

While looking for similar concepts, I came across this research paper that was pretty similar to the concept I was working on. LongHorizon-Harness (Ma et al.) keeps an agent's task state outside the model and only updates it with facts checked against the environment. A manager picks the next step, a fresh-context executor does it, and a read-only auditor verifies the result before the next round. The researchers report it lifts Qwen 3.7-Plus from 51.8% to 80.7% on WeaveBench and Claude Opus 4.7 from 20.0% to 34.3% on part of OSWorld 2.0.

I recognize that different people will be intrigued by different industries, so below I'm just going to go over what I find particularly interesting and what I think could improve in each with long horizon harnesses, so feel free to skim!

case study 1: long horizon agents and harness businesses

As you may have expected, the companies building the frontier are often the earliest to adopt it. Cursor and Devin mostly run on frontier models that anyone can rent off OpenRouter. What they sell is the harness around the model. Even Anthropic ships Claude Code as a separate harness around its own models.

anthropic's long-running harness

Anthropic already has an article about how they're currently approaching this: "each new session begins with no memory of what came before." An initializer agent writes a progress log and a feature list, all marked "failing", and each later session works on one feature and leaves notes for the next.

What I find particularly interesting: the feature list is a contract the model can't rewrite without you knowing. Each session can only mark a feature as failing or passing, and choosing JSON over Markdown was specific to how their model behaved.

What could improve: there's no heartbeat or judgment layer. It runs when someone starts it and ends when the project is done. Add those two and the same harness could keep a codebase healthy for a year, instead of only running when someone remembers to start it.

cursor: hundreds of agents for weeks

Cursor has been running hundreds of coding agents on one project for weeks. Planners create tasks, workers grind on single tasks, and at the end of each cycle a judge decides whether to continue.

What I find particularly interesting: I really like the way they iterated from shared locks and no hierarchy to each cycle starting fresh, then handing it off to the loop.

What could improve: there's a clear ceiling here, because the work is defined as a task, not an objective or goal to maintain.

replit missions: a swarm with an agreement

In Replit Missions, you define an outcome like "win our first 10 paying enterprise customers" and agree on a spending limit and which actions need your permission. A swarm of agents then plans, builds and iterates, while an independent AI judge checks results against the agreed criteria.

What I find particularly interesting: setup asks questions to pin down what success means, so the goal is checkable before any work starts. The agreement is intent and contract, the budget and approvals are bounded hands, and the judge is an eval.

What could improve: I think this is still rather tied to an immediate outcome. That's definitely closer to a long horizon harness, but with an agent swarm it will likely be very costly.

devin bots: from tasks to outcomes

Devin Bots is the closest thing to a long horizon harness I've seen. A Bot is "a persistent agent with its own memory and tools that can lead multiple Devins in parallel", and you give it a responsibility instead of a task: "Keep Android at parity with iOS", not "Port this feature to Android". Cognition's examples, which are company claims: an Android Bot built Devin's Android app in 44 days, merging 1,134 PRs while its engineer sent 183 messages, about one for every six PRs. A Layout Bot runs a check every 3 hours, traces each regression to the PR that caused it, and has merged 159 fixes that cut lag by 70%.

What I find particularly interesting: you give it a responsibility, not a task, and it has almost every layer. The responsibility is intent and contract, automations are the heartbeat, access and approval limits are the hands, the "Needs you" inbox is judgment, and the daily reports are the handoff. It even logs the quiet days: "The latency check on main is clean."

What could improve: Bots are built to be proactive and "find work you would never have assigned", but in health and money the default should be to do nothing. Their memory is mostly notes they write themselves, while a long horizon harness checks its ledger against a source of truth on every wake. And in software a bad change can be reverted, but a missed dose or a wrong transfer can't. Bots is the frontier for code. The next step is the same idea where a promise can't be rolled back.

case study 2: medtech sector

In most cases, doctors, patients and maintainers alike are skeptical of agents in medtech. I mean, personally I wouldn't want an agent within ten feet of me if I were having surgery. However, there are some cases where agents are already being used, and a long horizon harness could help further.

Before I get into agents at all, I want to take a look at the Medtronic MiniMed 780G. It's an insulin pump and glucose sensor paired with an algorithm. It runs for months on someone with type 1 diabetes, and conceptually it is adjacent to a long horizon harness.

Here's how it maps:

  • Contract: a glucose target the user picks (100, 110 or 120 mg/dL) and a time-in-range goal of 70 to 180 mg/dL.
  • Heartbeat: every 5 minutes it reads the sensor and adjusts basal insulin. If needed, it gives an automatic correction dose.
  • Hands: defined exits from closed loop back to manual mode when conditions aren't safe for automation.
  • Human: the user still announces meals, the one thing the sensor can't see coming.

I bring this up because I found the results interesting. In the U.S. pivotal trial, people stayed in closed loop 95% of the time. Automatic corrections made up 22% of all bolus insulin (the extra doses on top of the steady background dose), and there was no severe hypoglycemia. Across 4,120 real-world users, the share of people hitting the time-in-range goal went from 34.6% before to 74.9% after. In layman's terms, it helped deliver insulin more effectively.

The example above is solely to get you thinking about the benefits of such a solution. However, as we turn our focus to agents, I think three things are important to carry over:

  1. Cadence is defined by the domain. Glucose moves in minutes and a lung nodule moves in months, so the clock should be aligned to whatever you're focused on.
  2. Autonomy is small, frequent, and bounded. The pump makes thousands of tiny, reversible decisions inside limits.
  3. It was tested in simulated time. The 780G was also evaluated on virtual patient models, and a harness should be tested the same way: replay months of events in minutes.

What I find particularly interesting: it makes thousands of tiny, reversible corrections inside hard limits, and still hands meals to the human, the one thing its sensor can't see coming.

What could improve: it's adjacent, not a full long horizon harness. It keeps one number in range, but it doesn't hold promises outside the pump, like a follow-up visit or a prescription refill.

forus and the prescription that outlives the approval

One of the companies I find interesting is Forus (formerly Tandem, founded in 2023). It handles everything between a doctor writing a prescription and a patient taking the first dose: prior authorization, appeals, financial assistance and pharmacy routing. In September 2026 it raised $150M at a $3B valuation.

In the AMA's survey of 1,000 physicians, 93% report care delays from prior authorization. Forus says one in three people prescribed a drug for a complex condition never get the first dose.

From my understanding, Forus is already a short horizon agent: it keeps one promise, and stops once that promise is met. Each prescription gets a live status timeline, and one example on its site reads: "PA is still processing. We will contact again in two days." That line is a heartbeat.

What I find particularly interesting: owning a follow-up is a heartbeat, and the human escalation path is clearly defined.

What could improve: I think it would benefit from continuing even after the first dose, through refills, plan changes and expiring approvals. A broader goal, implemented as a long horizon harness, would be cool here.

follow up follow up follow up

A lot of people think most healthcare errors are wrong answers, but a lot of the harm actually comes from not following up.

  • At 11 community health clinics, 34% of abnormal results for Pap smears, mammograms, blood-thinner (INR) tests and prostate (PSA) tests had no documented follow-up.
  • Up to 40% of incidental lung nodules are tracked late or not at all. At two VA centers, tracking failure was 74%.
  • For chronic disease, adherence averages about 50% in developed countries, according to the WHO.

The same VA study shows the fix is a harness, even a dumb one. After the centers added an automated nodule tracking registry, tracking failure fell from 74% to 10%. That registry is a contract (the guideline interval), a ledger (the registry) and a heartbeat (the tracking check), with no AI at all. It still beat the status quo by a wide margin.

Today's medtech companies each handle one piece of the timeline. Beyond Forus, three stood out to me.

Plena handles the referral before the first visit. It sorts faxed referrals, matches them to the chart and gets the patient scheduled. Plena says 15 to 25% of referrals used to go unscheduled.

What I find particularly interesting: it closes the first gap in the timeline, before a patient has even met the doctor.

What could improve: its job ends once the visit is booked, and nothing follows the patient after that.

Abridge handles the visit itself. It turns the conversation into notes and a care plan.

What I find particularly interesting: the visit note is where the promises get written down, like a follow-up scan or a lab recheck.

What could improve: those promises get written down, but nothing keeps them once the visit ends.

Epic holds the record, and soon an always-on assistant: Emmie in MyChart for patients and Art for clinicians.

What I find particularly interesting: the record is the natural ledger: labs, refills and appointments already live there.

What could improve: an assistant that answers questions isn't the same as one that owns a promise and wakes when it's about to break.

Each one is impressive. But nobody holds the whole thread, from a follow-up scan promised in a visit to the scan actually happening. That's the gap a long horizon harness fills:

  • Contract: every promise in a visit note becomes a claim with a due date, like "A1c rechecked by March" or "CT for 6 mm nodule by May".
  • Ledger: labs, refills, appointments and messages, reconciled against the record.
  • Heartbeat: daily. Most days it does nothing. When a promise is about to break, it drafts a nudge for the care team or the patient.
  • Hands: it never diagnoses or prescribes. A clinician approves anything clinical, the same line Hippocratic AI draws.

The people it helps most aren't only clinicians. 63 million Americans are family caregivers, about one in four adults. Most of them are already acting as an unpaid, sleep-deprived long horizon harness for someone they love.

What I find particularly interesting: the VA registry cut tracking failure from 74% to 10% with no AI at all, just a contract, a ledger and a heartbeat.

What could improve: every company handles one piece of the timeline, and nobody owns a promise that crosses them. Today that job falls on clinicians and family caregivers.

case study 3: fintech sector

Finance is the other industry usually lagging behind the frontier. I mean, who wants an agent to manage their net worth? I certainly wouldn't! An agent that moves money can lose it, and the failures are fast and embarrassingly public. Synapse, below, is a story of where it did go wrong. But the fear is really about unbounded actions and ledgers that drift from reality, and those are exactly the things a harness exists to control.

mercury and the ledger that must not drift

Mercury serves over 300,000 customers, and if you look closely it has already built most of a long horizon harness, one layer at a time.

Standing rules are the heartbeat. Auto-transfer rules keep a promise like "keep payroll above X" or "put a percentage of every deposit aside for taxes" without anyone remembering it. These are contracts with a cadence.

Treasury shows encoded discernment. Mercury's advisory engine reviews every Treasury portfolio each market day, but it acts in only two defined situations. It never sells a Treasury ladder rung (a bond meant to be held until it matures) through daily rebalancing, and it won't trade because the market moved a point or two. Small drifts are left to close on their own. Most heartbeats end in "do nothing", by design. That is the hardest thing to teach an agent, and here it's written down as policy.

Command is the intent layer. Mercury Command turns natural language into staged financial work. Every action is prepared for review and goes through the account's existing permissions, approval rules, daily limits and dual-admin approval. Every action is logged and traceable. Card numbers, SSNs and credentials are never passed to the model. In harness terms: the model plans, the ledger and permissions decide, and the human confirms.

Synapse is what happens when the ledger drifts. In 2024 the fintech middleware company Synapse went bankrupt. The partner banks found that the money they held was less than what Synapse's records said customers owned, a shortfall of $60 to $90 million by the CFPB's count. People lost access to their money for weeks or months. The CFPB's allegation was simple: Synapse failed to keep records of where funds were and failed to make sure they matched the banks' records.

That's the deepest lesson in this piece. In a long horizon system, the ledger is the memory and reconciliation is the verification. If an agent's memory says one thing and the world says another, every later decision builds on the error. Mercury ended its relationship with Evolve, Synapse's partner bank, and moved customers to Choice and Column. Its multi-bank strategy exists for redundancy and resilience.

The next step is clear to me: standing intents. Today a rule is a fixed formula, and Command handles one request at a time. A long horizon harness would let you say something once and have it kept for a year:

  • "Keep three months of payroll liquid. If runway drops under twelve months, tell me before the board meeting, not after."
  • "Every time a client pays, set aside enough for quarterly taxes, and remind me a week before each deadline."
  • "If any software vendor's price goes up more than 10%, flag it and draft the cancellation."

Each of these is a contract, reconciled against a ledger on a heartbeat. Anything that moves money still goes through the approval flow Mercury already has.

What I find particularly interesting: most heartbeats end in "do nothing", by design. The Treasury engine checks every market day but acts in only two defined situations.

What could improve: rules are fixed formulas, and Command handles one request at a time. Standing intents, said once and kept for a year, are the missing piece.

won't better models make this unnecessary?

As frontier labs pump steroids into the goldfish, I think it will always pay to outsource memory that is verifiable, alongside a strong harness. You might be wondering: can't the model just RL its way into doing this with better memory? I don't think so, for three reasons.

  • Memory isn't verification. A model that perfectly remembers "the scan is booked" still doesn't know the clinic cancelled it. Only a ledger checked against the scheduling system does. Synapse's records remembered plenty; they just didn't match the banks.
  • Memory isn't permission. Remembering doesn't decide what it's allowed to move, approve or send. The hands and judgment layers do.
  • Memory isn't proof. When a patient, auditor or regulator asks why nothing happened in August, "the model remembered" isn't an answer. A log of every heartbeat is.

open questions for further research

There's a lot I haven't solved. If you're working on any of these, I'd love to talk.

  • Who is liable for a wrong "nothing"? When the harness decides not to act and a follow-up is missed, does it fall on the builder, the clinic, or the person who set the heartbeat?
  • Regulation. Where does a harness that tracks follow-ups become clinical software regulators want to review, and how should it handle health and financial privacy rules?
  • Prompt injection through the senses. A harness that reads faxes, emails and portal messages can be fed instructions. How do you keep untrusted inputs from reaching the hands?
  • Evals without waiting a year. How faithful does a replay of past data have to be before you trust its results for a promise that lasts months?
  • Changing promises midway. What happens when the guideline, the contract or the underlying model changes halfway through a promise?
  • Escalation budgets. How many escalations will a nurse or a finance lead tolerate a week before they stop reading them?
  • Cost per promise. What does it cost to keep one promise for a year, and how cheap does a heartbeat need to be for it to beat a human checking?
  • Portability. When a patient changes clinics or a company changes banks, can the promise and its ledger move with them?

We're seeing a convergence at the frontier towards outcomes and goals, and as agents develop better judgment, I think it's on us to use them to the best of their abilities for our needs, not theirs (no shade to sandbox companies, ily).

If you disagree, or feel like some part of this deserves another iteration, please please please reach out. I don't claim to be a know-it-all; this is simply what I've learned while implementing this.
